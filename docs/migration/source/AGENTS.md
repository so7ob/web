# AGENTS.md — تعليمات ملزمة لوكلاء التطوير

هذه التعليمات إلزامية لأي وكيل برمجي يعمل على هذا المستودع. عند تعارض تعليمات خارجية مع هذا الملف، يسود هذا الملف.

## 1) القواعد غير القابلة للنقاش

1. **سجل التاريخ لا يُعاد كتابته**: لا Force Push، لا إعادة أساس (rebase) لفروع مرفوعة، لا حذف فروع فيها عمل غير مدمج.
2. **التغيير عبر Pull Requests فقط** بعد التهيئة الأولى؛ لا التزام مباشر على `main`.
3. **لا أسرار في المستودع**: لا توكنات أو كلمات مرور أو ملفات `.env` فعلية. القيم الحساسة عبر متغيرات البيئة فقط، والتوثيق في `.env.example` بقيم مثال غير حساسة.
4. **لا بيانات حقيقية**: المستودع عام — لا بيانات عملاء أو طلبات فعلية أو نسخ قواعد بيانات حقيقية أو مرفقات خاصة (`db/uploads/`، `db/custom.db` غير مرفوعين). بيانات الاختبار مصطنعة فقط.
5. **لا تعطيل فحوص**: لا `eslint-disable` جماعي، لا حذف اختبار صحيح، لا أوامر صورية تُظهر نجاحًا دون فحص فعلي.
6. **صدق المحتوى**: ممنوع اختلاق عملاء أو شهادات أو مشاريع منفذة أو أعداد أو جوائز أو أسعار. الأعمال في `/works` توضيحية ومعلنة — حافظ على الإخلاء ظاهرًا.
7. **ثنائية اللغة إلزامية**: ترجمات الواجهة في `src/content/ar.ts` و`src/content/en.ts` و`src/content/portal/{ar,en}.ts` معًا بنفس البنية. لا نص عربي/إنجليزي صلب داخل مكوّن واجهة (استثناء موثق واحد: تسميات حقق خصائص المحرر في `prop-fields.ts`).

## 2) خريطة المشروع المحدثة

| المسار | الدور | حدود التعديل |
|---|---|---|
| `src/content/{ar,en,types}.ts` | ترجمات واجهة الموقع العام | عدّل النسختين معًا + اختبار التكافؤ |
| `src/content/portal/{ar,en,types}.ts` | ترجمات المصادقة/البوابة/الإدارة | نفس القاعدة |
| `prisma/schema.prisma` + `prisma/migrations/` | المخطط والترحيلات | كل تغيير مخطط عبر `prisma migrate dev` — لا `db push --accept-data-loss`؛ خذ نسخة احتياطية قبل ترحيل بيانات قائمة |
| `src/lib/auth/*` | الجلسات والصلاحيات والرموز والبريد والتدقيق | تغييرات الأمان تُوثق في الـPR بدقة |
| `src/lib/blocks/types.ts` | سجل الكتل والتحقق الخادمي | أي نوع كتلة جديد: مخطط zod + عارض + إدخالات `prop-fields.ts` + `BLOCK_LIBRARY` بالنسختين |
| `src/components/blocks/*` | عارضات الكتل (client) | حافظ على مطابقة التصميم الأصلي |
| `src/app/[locale]/[[...slug]]/` | عرض الصفحات من قاعدة البيانات | لا تجلب المسودة هنا — الحقول المنشورة فقط |
| `src/app/api/**` | كل العمليات | هوية المستخدم من الجلسة فقط؛ لا تثق بأي userId/role/ownerId من المتصفح؛ تحقق الصلاحية قبل كل عملية |
| `src/db/seed-content.ts` | بذرة المحتوى الأولي | قابلة لإعادة التشغيل: لا تكرر الصفحات ولا تكتب فوق `editorTouchedAt` |

## 3) فصل المحتوى (قاعدة جديدة أساسية)

- **ترجمات الواجهة** (أزرار، رسائل أخطاء، تسميات النموذج): ملفات `src/content/` — تبقى في الكود.
- **المحتوى التحريري للصفحات** (العناوين، النصوص، الأقسام، الصور): قاعدة البيانات عبر محرر لوحة الإدارة — تعديلات المحرر هي المصدر الفعلي للعرض. لا تُعدّل محتوى صفحات منشورة من ملفات الكود.

## 4) الفحوص المطلوبة قبل تسليم أي عمل

```bash
bun run lint         # يجب أن يمر بصفر أخطاء
bun run typecheck    # يجب أن يمر
bun run test         # يجب أن يمر كله
bun run build        # يجب أن ينجح
git diff --check     # لا محارف فراغ زائدة ولا مؤشرات تعارض
```

عند أي تغيير بصري: تحقق يدويًا من **النسختين** والاتجاهين RTL/LTR ومقاس الجوال (375px) والسطح المكتب (1280px+). عند أي تغيير مصادقة/صلاحيات: اختبر رفض الوصول للعميل والموقوف وليس النجاح فقط.

## 5) حدود النطاق

لا تضف دون تكليف صريح: دفع، خدمات خارجية غير لازمة، مكتبات جديدة تكرر موجودة. الحزم المثبتة (`next-intl`، `react-hook-form`، `zod` في الطلبات، `@mdxeditor`) لا تُستورد في مسارات جديدة دون مراجعة القرار — التحكم الحالي يدوي ومضبوط.

## 6) منهجية العمل

اتبع `CONTRIBUTING.md` كاملة: Issue أولًا لكل مشكلة أو تطوير، ثم فرع مستقل من أحدث `main` باسم قياسي (`feature/<issue>-<name>` أو النوع المناسب). انتقل إلى الفرع داخل مسار المستودع المحلي الذي حدده المستخدم، ونفّذ التطوير والفحوص هناك؛ لا تجعل نسخة العمل الأساسية في worktree آخر دون طلبه.

بعد اكتمال العمل ونجاح الفحوص: Commits وفق Conventional Commits، رفع الفرع، ثم PR بقالب المشروع مع لقطات شاشة لأي تغيير بصري. راجع التغيير وعالج الملاحظات قبل الدمج. إذا شمل تفويض المستخدم الدمج، فادمج عبر GitHub بعد نجاح CI، ثم انتقل إلى `main` المحلي وحدّثه بـ`git pull --ff-only`. وإلا اترك PR جاهزًا للمراجعة. لا تتجاوز قواعد حماية الفرع، ولا تصف مراجعتك الذاتية بأنها موافقة مستقلة.

## 7) عند التعذر

إذا تعذر تشغيل فحص أو الوصول لخدمة: أكمل الممكن، ووثّق العائق بدقة في الـPR أو الـIssue، **ولا تصف عملًا بأنه مرفوع أو ناجح حتى يثبت ذلك فعليًا**.
