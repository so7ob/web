# دليل المساهمة — so7ob Website

هذا المستودع مرجع مركزي للكود والتوثيق وسجل التغييرات. التزم بالمنهجية أدناه؛ فهي شرط لقبول أي طلب سحب.

## 1) قبل البدء

1. تحقق أن فكرتك لا تتعارض مع Issue قائم.
2. افتح **Issue** جديد (قالب ميزة أو خطأ) يتضمن: المشكلة والهدف، نطاق العمل والاستثناءات، معايير القبول، الملفات المتأثرة، مخاطر التوافق أو البيانات، وخطة التحقق والاختبار.
3. لا تبدأ كتابة كود لعمل غير موثق في Issue — الاستثناء: تصحيح خطأ إملائي واضح.

## 2) الفروع

انطلق دائمًا من أحدث `main`، واستخدم أسماء فروع بصيغة:

```
feature/<issue-number>-<feature-name>   # ميزة جديدة
fix/<issue-number>-<bug-name>           # إصلاح خطأ
docs/<issue-number>-<topic>             # توثيق
chore/<issue-number>-<task>             # مهام صيانة
```

فرع واحد لكل موضوع. قسّم الأعمال الكبيرة إلى مراحل قابلة للمراجعة أو عدة فروع.

نفّذ الانتقال إلى الفرع والتطوير داخل مسار المستودع المحلي الذي حدده المستخدم (في هذه البيئة: `/root/So7ob/Website`). حافظ على أي تغييرات محلية قبل تبديل الفرع. لا تنقل نسخة العمل الأساسية إلى worktree آخر دون طلب المستخدم؛ يمكن عزل قواعد بيانات الاختبار والملفات المصطنعة خارج المستودع.

## 3) الـCommits — Conventional Commits

```
feat: add bilingual service pages
fix: preserve project form data after submission failure
docs: document local setup
chore: update dependencies
refactor: extract shared validator
test: cover duplicate submission guard
```

- الرسالة تصف ما يفعله الـcommit، لا ما كنت تنوي فعله.
- Commit واحد = تغيير مترابط واحد.

## 4) قبل فتح طلب السحب

شغّل الفحوص محليًا وتأكد من نجاحها جميعًا:

```bash
bun run lint && bun run typecheck && bun run test && bun run build && git diff --check
```

ثم أضف/حدّث ما ينطبق:

- اختبارات للسلوك المتأثر (خاصة تحقق النموذج والحمايات).
- تحديث التوثيق إذا غيّرت سلوكًا أو إعدادًا.
- ترجمة أي نص جديد في **اللغتين** `src/content/ar.ts` و`en.ts` (اختبار التكافؤ سيفشل غير ذلك).
- فحص الاتجاهين RTL/LTR والعرض على الجوال إن كان التغيير بصريًا.

## 5) طلب السحب

استخدم قالب `.github/PULL_REQUEST_TEMPLATE.md` ووضّح:

- سبب التغيير + ربط الـIssue (`Closes #NN`).
- ما تغيّر وسلوك الموقع الناتج.
- صور الواجهات عند أي تغيير بصري.
- نتائج الفحوص المحلية.
- الإعدادات المطلوبة والقيود المتبقية.
- طريقة التراجع عند استدعاء طبيعة التغيير.

ارفع الفرع بعد اكتمال التطوير والفحوص المحلية، ثم افتح PR وراجعه وعالج الملاحظات. وثّق ما فُحص وحدود الاختبارات؛ المراجعة الذاتية ليست موافقة مستقلة من شخص آخر.

الدمج عبر GitHub فقط بعد نجاح CI واستيفاء قواعد حماية الفرع واعتماد المستخدم. إذا طلب المستخدم صراحة تنفيذ الدورة حتى المراجعة والدمج، فهذا تفويض بالدمج ضمن النطاق المحدد، ولا يُطلب الإذن نفسه مرة أخرى. دون هذا التفويض، اترك الطلب **جاهزًا للمراجعة**. لا تتجاوز حماية الفرع أو تدمج تغييرًا بفحوص فاشلة.

## 6) معايير القبول العامة

- لا نصوص تجريبية (Lorem Ipsum) ولا أقسام فارغة.
- لا اختلاق بيانات: عملاء، شهادات، أرقام، سنوات خبرة، أسعار أو مدد غير معتمدة.
- لا أسرار في الكود ولا مفاتيح في الواجهة؛ كل السر عبر متغيرات البيئة و`.env.example` توثيقًا.
- الوصول وفق WCAG 2.2 AA: تباين، تسميات، تركيز مرئي، لوحة مفاتيح، تقليل الحركة.
- ممنوع: Force Push على الفروع المفتوحة للمراجعة، تعطيل فحص لازم، حذف اختبار صحيح لتمرير البناء.

## 7) ما بعد الدمج

- انتقل إلى `main` في مسار المستودع المحلي وحدّثه باستخدام `git pull --ff-only`، وتحقق من تطابقه مع `origin/main` كي تظهر التطويرات للمستخدم في جهازه.
- إذا احتاج التغيير ترحيل بيانات محلية، فاتبع دليل الترحيل والنسخ والاستعادة قبل تطبيقه؛ دمج الكود وحده لا يحدّث قاعدة البيانات.
- احذف فرع العمل بعد الدمج إن لم يعد مستخدمًا؛ احتفظ به إذا كانت روابط توثيق أو مراجعة تعتمد عليه.
- أي متابعة تعالجها كـIssue وفرع جديد بالمنهجية نفسها.
