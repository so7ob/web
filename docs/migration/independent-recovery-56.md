المرجع الحالي عند بدء العمل: develop `85ab40b8c7558f0590c684c4eb1031fbae678a66`،
وmain `2a26ee0c19bec249ea394d5584028ddff599b6dc` بنفس شجرة الملفات.

## ما يحتاج اعتماد المالك

- مضيف staging مستقل عن مصدر النسخة، وحسابات وصلاحيات منفصلة، وتحديد المسؤول عن التشغيل والتراجع.
- هدف RPO (الحد المقبول لفقد الكتابات) وهدف RTO (زمن عودة الخدمة): **غير معتمدين وغير مقاسين**.
  يسجل المالك قيمة لكل منهما قبل الاختبار؛ لا تعتمد قيمة تجارية افتراضية من هذه الوثيقة.
- مخزن نسخ خارج المضيف مع سياسة احتفاظ واختبار وصول، ومخزن أسرار مستقل، وآلية مصادقة على مصدر الأرشيف.
- نافذة وقف الكتابات ونقطة السماح بفتحها، وخطة التعامل مع رسائل SMTP ذات النتيجة uncertain.
- حماية main/develop بفحوص فعلية ومراجعة مستقلة؛ تبقى إعدادات GitHub الخارجية بانتظار الاعتماد والتطبيق.
  تغيير YAML لا يفعّل الحماية. راجع PR #42 قبل اعتماد أسماء الفحوص.

## تجهيز staging قبل التجربة

ثبّت Node/npm بالإصدارات المقفلة وMariaDB المتوافقة، وmariadb/mariadb-dump وtar، وتحقق من
وقت UTC والمساحة والحقوق. استخدم إصدارًا مبنيًا مثبت SHA وبصمات artifacts وpackage-lock؛
لا تعتمد أحدث فرع غير مثبت. احتفظ بنسخة الإصدار السابق وبصمتها. شغّل API والعامل كخدمتين مستقلتين.
ضع DATA_DIR خارج دليل الإصدار، بملكية حساب الخدمة، واحتفظ بالمرفقات خارج public.
تحقق من إعدادات reverse proxy وTLS وSITE_URL وWEB_ORIGIN وSecure cookies كما في ops/.

البيانات هنا اصطناعية. امنع الخروج إلى SMTP/Webhook الحقيقيين واستخدم مستقبِلَين محليين؛
لا يكفي EMAIL_DEV_MODE لإثبات منع اتصال خارجي لكل أنواع المهام. اختبر التسجيل والجلسات
والأدوار والملفات الخاصة واللغتين وSSR وروابط متابعة الضيوف والحفظ والنشر بالبيانات الاصطناعية.
لا تدخل بيانات .env أو مفاتيح أو dump أو مرفقات إلى Git أو مخرجات CI.

## إجراء الاستعادة المقترح للمشغّل المعتمد

1. سجل وقت حادث الاختبار وبصمة الإصدار وأسماء الخدمات والقاعدة ومسارات الملفات دون أسرار.
   أوقف API/كل مصادر الكتابة والعامل، وتحقق فعليًا من توقفها. `MIGRATION_WRITES_PAUSED=yes`
   إقرار تشغيلي، وليس آلية توقف الخدمات. امنع التشغيل التلقائي للعامل على الوجهة.
2. استرجع خارج المضيف أرشيف الإصدار والنسخة الموثوقة للقاعدة والملفات وmanifest.
   تحقق من مصدر الأرشيف ثم البصمات؛ checksum يثبت سلامة البايتات ولا يثبت الثقة بالمصدر،
   وSQL قابل للتنفيذ. طابق نقطة اتساق القاعدة والملفات وسجل عمر آخر كتابة مستعادة.
3. استرجع المفاتيح من المخزن المستقل بحقوق مقيدة: OUTBOX_KEY نفسه لفك حمولة MailJob وWebhookJob،
   وAUTH_SECRET وإعدادات الاتصال والخدمات الموافقة للإصدار. لا تولّد مفتاح طابور بديل لنسخة قديمة،
   ولا تختبر المفتاح بتشغيل العامل. سجّل هوية إصدار السر ونجاح الاسترجاع، لا قيمته.
4. أنشئ قاعدة وجهة **فارغة جديدة** ودليل ملفات **جديدًا**. لا تنفذ migrate أولًا في وجهة الاستعادة؛
   الأرشيف يعيد المخطط وترحيلاته. لا overwrite أو reset لوجهة بها بيانات.
   استخدم الأوامر التالية فقط بعد تعيين بيئة الوجهة المعتمدة ومتغيرات المسارات؛ هذه أمثلة لم تُنفذ هنا:

   ```sh
   export MIGRATION_WRITES_PAUSED=yes
   npm run data:backup -- --mode restore --directory "$RECOVERY_ARCHIVE" --uploads "$RECOVERY_UPLOADS" --confirm-database "$DATABASE_NAME"
   npm run db:check
   npm run data:recovery-check -- --confirm-database "$DATABASE_NAME"
   ```

   عقد CLI: `packages/server/src/migration/backup-cli.ts` و`recovery-cli.ts`.
   `data:backup --mode restore` يتحقق من بصمات SQL/الملفات وخلو الوجهة ويعيد كليهما.
   شغّل الأمر من الإصدار الموافق للنسخة. الترقية إلى إصدار أحدث عملية منفصلة بمراجعة migrations،
   وتجربة على نسخة معزولة ونسخة رجوع؛ لا تُجرى ضمن هذه المهمة.
5. قارن أعداد وبصمات الجداول والملفات والمراجع والملكية والحقوق مع manifest آمن. تحقق من بقاء
   المعرّفات والتواريخ والجلسات وهاشات bcrypt؛ لا تعيد تشفير كلمات المرور. تحقق من عدم الاعتماد
   على مسار المضيف المفقود أو تبعياته أو مفاتيحه المحلية.
6. قبل العامل: شغّل recovery-check مع المفتاح المستعاد، وسجل أعداد الحمولات المفحوصة فقط.
   راجع بأداة قراءة أو استعلامات معتمدة أعداد وعمر حالات queued/retry/leased/sending/uncertain/failed
   وإيجاراتها في الطوابير، دون payload. SMTP accepted لا يعني وصولًا إلى صندوق المستلم.
   لا تعِد إرسال uncertain جماعيًا ولا تغيّرها إلى queued لتجميل المؤشرات. أي reconciliation
   لنتيجة إرسال مبهمة يحتاج دليلًا وقرارًا مستقلًا. حافظ على قواعد الإيجار ومنع التكرار.
7. على staging مع منع الخروج الحقيقي: افتح API، تحقق من readiness والرحلات والصلاحيات وقراءة
   المرفقات. readiness يثبت جاهزية API/قاعدة البيانات فقط. شغّل العامل منفصلًا بعد نجاح فحص المفاتيح،
   وتحقق من عمله وheartbeat المستقل (إذا دُمج PR #53). أوقفه مجددًا لإثبات تدهور مراقبته مع بقاء API جاهزًا.
8. سجّل وقت عودة الخدمة المتحققة ووقت آخر كتابة مستعادة، واحسب RTO الفعلي من بداية الحادث
   إلى اجتياز الرحلات، وRPO الفعلي من الحادث إلى آخر نقطة كتابة متسقة. قارنهما بالأهداف المعتمدة،
   مع حجم البيانات/الملفات وسرعة النقل والعتاد وإصدار البرنامج. لا تعمم قياس fixture صغير على الإنتاج.
9. لا تفتح كتابات إنتاج من هذه التجربة. في خطة معتمدة لاحقًا يكون الرجوع الكامل قبل فتح الكتابات؛
   بعد فتحها لا تستبدل القاعدة والملفات بنسخة قديمة فتفقد أعمالًا جديدة: احفظها وتَعافَ للأمام.

## الدليل المطلوب لإغلاق حد فقد المضيف

هوية بيئة مستقلة، وعدم إتاحة المضيف الأصلي أثناء التجربة، وإثبات جلب النسخة والأسرار من مخازنها،
وبصمات الإصدار/الملفات وأعداد الجداول، ونتيجة فحص المفاتيح قبل العامل، ورحلات الاستخدام والصلاحيات،
وحالات الطوابير قبل/بعد، وقياس RPO/RTO وتوقيع مراجعة المسؤول. جميع الأدلة منقحة.

**الحالة الآن: غير متحقق لغياب البيئة المستقلة والتكليف التشغيلي.** النجاح المحلي أو CI في
`npm run test:restore` يبقى تجربة اصطناعية على المضيف نفسه. لا نشر أو ترحيل إنتاج أو حماية GitHub
فُعّلت. تراجع هذه الحزمة هو revert للوثيقة فقط، ولا يغير خدمات أو بيانات.
