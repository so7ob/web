# Audit evidence: contracts and operational boundaries

Issue: https://github.com/so7ob/web/issues/70. Base: `65dba5f99c46f76f7c70aa8ee283921077b22945`. Branch: `feat/70-audit-investigation`. No stacked dependency: request fix #60 and diagnostics #64 are merged; #59/#61 closed. No deployment or merge is authorized by this implementation.

## Data and identity

`AuditLog` retains every existing ID/createdAt/details column. An additive migration supplies version, event code, category, sensitivity, outcome, source, reason, safe resource reference, actor snapshot, diff payload, server correlation/error IDs, batch ID and recorded UTC time. It drops the actor foreign key so deleting a User cannot rewrite history. The application never updates original events. The actor's name/role/email at recording time are independent of User; actorEmail and the existing ipHash projection require `audit.sensitive.view`. ipHash is not an IP address.

Version 0 is an adapter, not a fabricated backfill. Old outcomes stay unknown, missing actor snapshots stay unrecorded, and missing recordedAt stays null. Known from/to fields are mapped only to their known action field. Unknown codes and malformed JSON never cause raw historical details to be returned. Dashboard and user activity consumers use the same projection.

`AuditValue` distinguishes missing, null, empty, redacted, unrecorded and a typed value. The diff has ordered arrays and nested allowlisted keys, depth four, 100 changed fields, 500-character scalar previews, 100 list values and a 32 KiB serialized payload cap. Content/page bodies, passwords/hashes, tokens, HTTP headers/bodies, conversation messages, private notes and files are never copied into evidence. Page operations use revision/state metadata. Context and diffs are sanitized again on read and in all report formats. Free-form case notes are separate authorized review data, not business conversation content.

## Transactions and concurrency

Existing request locks/sparse DTO contracts are retained: absent fields do not select another operation, null removes an assignee, invalid repeated status transitions remain 409. Business success and its final event/outbox insert commit together. Mandatory writer failure rolls back the business change. Equality attempts are explicit `no_change`; no value-based deduplication collapses legitimate operations. There is no exactly-once claim for arbitrary HTTP retries without an operation ID.

Bulk archive/restore selects changed resources under locks and writes one event per changed resource, plus batch.completed(requested/unchanged/count). Metrics count the summary as an event but exclude its pseudo-resource from distinct business resources. Request IDs in resources are not HTTP correlation IDs. The server-generated diagnostic requestId is the correlationId; no browser actor/source/outcome is trusted.

Required HTTP security denials/failures record independently after the business transaction/response, with bounded 128 in-flight writes. Overflow or storage failure records a sanitized diagnostic and does not change the response. Process death in this post-response interval can lose attempt evidence; success evidence remains transactional. Authentication failures do not assert that an unauthenticated requester owns an account. Opening the workspace/detail records at most once per user/resource per five-minute UTC bucket. Polling does not create access events.

## Storage model

AuditWork is the transactional alert outbox. AuditReport stores job ownership, sensitivity, lease, attempt, filters, counts, checksum and expiry. AuditView/AuditPreference are private to one user. AuditBookmark is separate from AuditCase/AuditCaseEvent/AuditCaseHistory. Cases have optimistic revisions and independent historical reviewers; closing a case cannot alter the original outcome. AuditRule/AuditAlert/AuditAlertEvent/AuditHealth/AuditPolicy are separate operational records.

There is no tenant model in this project. `audit.view` intentionally reads redacted platform-wide evidence. All entrypoints require it. New permissions are independent: audit.export, audit.review, audit.cases.manage, audit.rules.manage, audit.policy.manage, audit.sensitive.view, audit.health.view. Only super_admin retains the existing universal bypass. Existing/custom roles receive no migration grant. Resource links and diagnostic links require their original permissions; deleted resources are identified on authorized detail reads.

## Query and export consistency

Search uses POST bodies, validated `[from,to)` instants with explicit offsets, parameterized SQL and fixed descending `(createdAt,id)` ordering. UTC is the explicit default display zone, independent of language. Page size 50, maximum 100. REQ-/S7-/INQ- searches are recognized resource-reference prefixes; UUID searches are exact HTTP correlation/error IDs; other free text uses substring search. HMAC cursors bind user, sensitivity, normalized filter/limit and one-hour expiry. This is live browsing: an older transaction that commits late may require refresh to appear. The legacy route is redacted and capped at 100 pages; new consumers use cursors. Authenticated audit responses use private/no-store.

A report worker starts `REPEATABLE READ` + `START TRANSACTION WITH CONSISTENT SNAPSHOT` on one connection, counts and reads keyset chunks on that connection, verifies the written count, fsyncs, renames the private file and only then commits completed status and its success event. An uncommitted older transaction is excluded from that snapshot even if its timestamp precedes the snapshot. A retry starts a new snapshot/attempt; completed files are immutable. Limits: 100,000 events, 256 MiB, five minutes, three attempts, 60-second renewable lease. Files expire after 24 hours; evidence does not expire with them. Cancellation fences completion. CSV cells are quoted and formula-prefixed, JSON is structured, printable HTML is escaped with RTL/LTR and translated field/value states. Browser Print/Save PDF is the supported PDF path.

The owner and current export/sensitivity permissions are checked at execution and download, including after role revocation. Promotion cannot increase the sensitivity of a previously queued redacted report. No public file links exist. The manifest lists event IDs, count, filters, snapshot time, bytes and SHA-256. `tools/audit/verify-report.mjs` verifies file bytes against that manifest, **not** event origin or truth.

## Rules, health and retention

Rules start disabled, run only for events after activation, carry a revision and rationale, and use event/window unique keys and cooldown. Security failures use fixed UTC windows and distinct HTTP correlations. Administrative-role grants target super_admin/ops_manager and newly granted sensitive permissions in custom roles. The effective permission delta is captured inside the user transaction, including a combined role/status change and invite acceptance; later role edits do not rewrite the alert input. The explicit list is AUDIT_SENSITIVE_PERMISSIONS (users.roles/suspend, pages.publish, settings.manage, audit.export/rules.manage/policy.manage/sensitive.view, diagnostics.manage); no automated account blocking. Exports use distinct business resource counts. Health evaluates rollback insertion probes and pending queue age, not absence of new business events. No external sending is enabled. A failed optional processor cannot roll back a committed business event or terminate other worker services.

Retention is unconfigured by default; data is preserved. The API offers policy configuration and dry-run only. The separate maintenance CLI requires an independently privileged database account, current audit.policy.manage actor, explicit apply opt-in and reviewed policy revision; each apply deletes at most 250 events under the same retention lock used by case hold changes. Held case evidence is excluded. There is no individual delete or clear-all endpoint. Restore must happen while writes are paused; after reopening, recover forward.

## Threat model

Application users cannot update/delete event rows through the application. A runtime account with per-table SELECT/INSERT on AuditLog cannot UPDATE, DELETE or ALTER those rows; explicit isolated tests verify this without breaking business transactions. Never grant global/schema ALL, inherited roles, proxy rights or DDL to that account. Migrations and retention maintenance require separate identities. A compromised service account can still append false events and manipulate non-evidence tables; a DBA can alter both evidence and checksums. These controls do not claim tamper-proof storage or ISO/SOC certification.

External signing/checkpoints or immutable storage need a separate trust domain, key custody, rotation, verification tooling and authorized infrastructure. They are documented extension points, not enabled integrations. Use vetted signing libraries/service APIs when that infrastructure exists; no custom cryptography is introduced here.
