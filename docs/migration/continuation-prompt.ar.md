# برومبت استكمال إنشاء النسخة المستقلة من Website

انسخ النص التالي كاملًا إلى دردشة جديدة. هذه نقطة تسليم بتاريخ 2026-10-03؛ تحقق من الحالة الحية قبل العمل، ولا تعتبر نتائج تاريخية إثباتًا للكود الحالي.

---

تصرّف بصفتك مهندس برمجيات أول ومعماري أنظمة ومسؤول ترحيل وضمان جودة. استكمل تنفيذ المهمة الرئيسية القائمة: إنشاء نسخة مطوّرة ومستقلة من أحدث نسخة منشورة على فرع Website/main وقت بدء الاستكمال، بكامل وظائفها وهويتها وبياناتها وصلاحياتها وروابطها، على البنية الجديدة، ورفع العمل إلى so7ob/web مع أدلة تكافؤ وطلبات سحب قابلة للمراجعة. المطلوب التنفيذ حتى استيفاء القبول، وليس تقريرًا أو مشروعًا هيكليًا. المهمة لم تكتمل بعد، رغم تنفيذ أجزاء كبيرة ونجاح فحوص مرحلية.

## 1 أ. تحديث مرجع Website قبل استكمال الترحيل

1. تحقّق بعملية قراءة من SHA الحالي لـ refs/heads/main في https://github.com/so7ob/Website.git، ثم استخرج لقطة ذلك الـSHA إلى مساحة مرجعية معزولة داخل مساحة عمل web. لا تغيّر ملفات أو origin أو فروع النسخة الأصلية، ولا تنقل .git إلى التطبيق المستورد. لا تعتمد على نسخة محلية قديمة أو على عبارة «أحدث نسخة» دون SHA موثق. إذا تعذر التحقق البعيد، وثّق المانع ولا تصف اللقطة القديمة بأنها الأحدث؛ أكمل فقط العمل المستقل عن التحديث.
2. قارن اللقطة الجديدة بمرجع الاستيراد السابق 5321b7fd11db421c83290b262f276811e5f04e5f، ثم قارن التغييرات بتنفيذ web الحالي. أعد جرد الوظائف والصفحات وAPI والصلاحيات والبيانات والترحيلات والملفات والترجمات والاختبارات وتعليمات التشغيل؛ الأعداد السابقة تاريخية وقد تتغير.
3. سجّل الفروق في docs/migration/source-refresh.md، مع SHA القديم والجديد وتاريخ التحقق وروابط المصدر والملفات المتغيرة وتأثيراتها وحالة نقل كل تغيير واختباره. حافظ على manifest الاستيراد القديم، وأضف خريطة وبصمات للتحديث دون محو سجل المصدر أو النسب.
4. شغّل اللقطة الجديدة محليًا على بيانات اصطناعية مستقلة، وسجّل بناءها واختباراتها ورحلاتها ولقطاتها وعيوبها السابقة قبل تعديل البديل. احتفظ بالأدلة القديمة وأنشئ مرجعًا جديدًا مرتبطًا بالـSHA الجديد؛ لا تستبدل التوقعات القديمة صامتًا أو تستخدم خطًا مرجعيًا جديدًا لإخفاء نقص في web.
5. انقل كل وظيفة وإصلاح وتغيير بيانات أو صلاحيات جديد إلى البنية المستهدفة واختبر تكافؤه. عالج التعارضات مع العمل المنجز يدويًا وبالدليل؛ لا تستبدل Nest/Vite/TypeORM بالكود القديم ولا تفقد إصلاحات الأمان أو وظائف web القائمة بسبب النسخ فوقها. وثّق أي حذف أو تغيير سلوك مقصود في المصدر بدل إسقاط وظيفة دون تفسير.
6. حدّث مصفوفة التكافؤ وأداة نقل البيانات والمخطط والاختبارات لتشمل المصدر المحدث. إذا لم توجد فروق، سجّل ذلك بالدليل واستكمل النواقص. لا ترحّل ثغرة مثبتة؛ حافظ على الإصلاح المحدود واختباره والاستثناء الموثق.
7. ثبّت SHA الجديد لبقية دورة التنفيذ لتكون المقارنة قابلة للإعادة. قبل التسليم أعد فحص main البعيد؛ إذا تقدم، سجّل الفروق وانقلها واختبرها ضمن دورة تحديث موثقة قبل الادعاء بالتكافؤ مع الأحدث. اذكر دائمًا آخر SHA شمله التسليم وأي تحديث لاحق لم يُنقل؛ لا تدّع متابعة مستمرة لتغييرات مستقبلية.

## 4. ما نُفّذ، ضمن حدود إثباته

- استيراد المصدر المثبت مع الخرائط والبصمات؛ بناء مرجعي معزول و133 اختبارًا و40 لقطة وقياسات أولية على بيانات اصطناعية.
- npm Workspaces: apps/web وapps/api وapps/worker، وحزم العقود والخادم. تشغيل Node 24.21.0 وnpm 10.8.2؛ React/Vite/React Router SSR ديناميكي داخل NestJS/Express؛ TypeORM/mysql2/MariaDB. اعتمد package-lock.json والإصدارات الفعلية، ولا تُجر ترقيات كبرى غير لازمة.
- مخطط الكيانات وترحيلات MariaDB صريحة، وأداة SQLite والملفات بأوضاع dry-run/apply/resume/verify، والتحقق من المعرّفات والعلاقات والقيم والبصمات وإعادة التشغيل والنسخ والاستعادة على بيانات اختبارية.
- جلسات خادمية وتحقق bcrypt القديم، وCSRF وOrigin والصلاحيات وحدود المحاولات وإبطال الجلسات، ورموز البريد والدعوات دون تمديد صلاحيتها، وتشفير حمولات البريد الحساسة.
- صفحات عامة SSR وأنواع الكتل الـ27، وشاشات المصادقة ونموذج الطلب الحقيقي، وتسع شاشات بوابة العميل مع المسودات والمحادثات والملفات والإشعارات والملف الشخصي والأمان وربط الطلبات.
- خدمات الإدارة والمستخدمين والصلاحيات وحماية آخر مدير، وواجهات الإدارة والمحرر الأصلي بالسحب والإفلات والتراجع والإعادة والحفظ التلقائي والتعارض والمعاينة والنشر والإصدارات والاستعادة. وجود التنفيذ لا يثبت كل رحلة أو خاصية بعد.
- طابور MariaDB دائم وعامل مستقل للبريد والمهام، مع حجز وleases وإعادة محاولة واستعادة، وإعدادات Nginx/systemd وCI. لا ادعاء exactly-once أو وصول البريد إلى المستلم بمجرد قبول SMTP.
- إصلاحات محدودة موثقة: ظهور Hero مع reduced-motion، وتعارض تحرير دقيق، وحماية الصفحة الرئيسية من فشل slug متكرر، وCSV injection، وتسلسل labels الإدارة لمنع اختلاف hydration، ومنع إدخال الملف الشخصي قبل جاهزية hydration كي لا يفقد أول تعديل.
- البيانات والملفات الإنتاجية لم تُقدَّم ولم تُرحّل ولم تُتحقق. لا تقدم الأدوات أو التهيئة الاصطناعية بوصفها ترحيل إنتاج.

## 6. أولويات الاستكمال

1. ثبّت الحالة الحالية والأعمال المحلية وCI، واعتمد أحدث Website/main ووثّق فروقه ومرجعه المعزول وفق القسم 1 أ قبل قبول التكافؤ. انقل تحديثاته إلى web وأكمل النواقص. حقق أيضًا في فشل الإشعارات المذكور، وأعد الفحوص اللازمة بعد الإصلاح. لا تعطل اختبارًا صحيحًا.
2. أكمل مصفوفة Feature Parity بندًا بندًا: المعرّف والمسار والأدوار والمدخلات والمخرجات والنجاح والفشل والبيانات والتنفيذ القديم والجديد والاختبار والحالة والدليل. اختبر رحلات العميل والدعم ومدير العمليات ومدير النظام والمحرر، لا مجرد تحميل الشاشة.
3. غطِّ كامل الإدارة والمحرر: خصائص كل نوع كتلة، السحب والترتيب والإضافة والتكرار والحذف والتراجع والحفظ والتعارض والنشر والاستعادة، وعمليات الطلبات والاستفسارات والردود والملاحظات الداخلية والتعيين والتصفية والأرشفة والجماعي والتصدير والوسائط والقوائم والإعلان والإعدادات والتدقيق والبريد. راجع خصوصًا تكافؤ معاينة البريد الآمنة؛ الاقتصار على metadata لا يثبت كامل الوظيفة.
4. أكمل عقود API القديمة ومحولات /api/v1 وOpenAPI/DTOs والحالات المرفوضة والتحميل والتنزيل والروابط العميقة والتحويلات وأكواد 404/403. لا تكسر عميلًا قديمًا بسبب تبديل مسار API.
5. جدّد المقارنة البصرية للعام والبوابة والإدارة والمحرر بالعربية والإنجليزية وRTL/LTR وعرضي 375 و1280، ولوحة المفاتيح وaxe وConsole/Network. احتفظ بالمرجع المجمد؛ عيب Hero المخفي موجود في المصدر مع reduced-motion، ومقارنة صور فارغة سابقة لا تثبت قبولًا بصريًا جديدًا.
6. تحقق من HTML العام وعناوينه ووصفه وcanonical وhreflang وOpen Graph وrobots وsitemap، ومن ظهور تغيير CMS المنشور فورًا وفق سلوك المصدر دون HTML قديم أو فارغ.
7. أكمل قياسات p50/p95 والاستعلامات وJavaScript لكل العمليات الأساسية والإدارة والمحرر بخمس جولات متكافئة. الحدود المثبتة: الفرق البصري المستقر ≤0.5% مع مراجعة بشرية، لا أخطاء axe جديدة، تراجع زمن ≤الأكبر بين 10% و20ms، زيادة JS الأولي المضغوط ≤5%، ولا N+1 جديد. لا تعدّل الحدود لإخفاء فشل.
8. اختبر أكبر CMS JSON مسموح به على MariaDB فعلية مع إعدادات packet وحدود الطلب المتسقة. نجاح وثيقة عربية نحو 480KB لا يثبت حد 160MiB؛ بيئة الاختبار استخدمت max_allowed_packet=256M وقد تختلف بيئة التشغيل.
9. أعد تجربة ترحيل شاملة للحالات الحدية والملفات والملكية وUTF-8/collation/NULL/JSON/UTC والقيود والتزامن، والتعارض والاستئناف وعدم التكرار، ومجموعات IDs والقيم الدلالية والبصمات والأيتام، وقراءة التطبيق الجديد لها. لا تستخدم SQLite أو mocks بدل اختبار فروق MariaDB.
10. أكمل تجربة استعادة تشغيلية تشمل الكود والبيانات والملفات والجلسات والطابور ومفاتيح التشفير، وتعطل العامل واحتمال قبول SMTP والاستعادة. اختبار استعادة قاعدة وحدها لا يكفي.
11. أزل الاعتماد التشغيلي الأساسي المتبقي على Next.js/Prisma/Bun بعد إثبات البدائل. توجد ملفات وأوامر reference انتقالية في الجذر؛ ميّز الأرشيف المرجعي عن اعتماد المنتج، ووثّق ما بقي، ولا تعلن الاكتمال مع اعتماد أساسي انتقالي.

- لم يُنشأ مدير شخصي للمستخدم دون بريده. الأمر المحلي بعد قراءة الدليل والتأكد من NODE_ENV=development والوجهة الصحيحة:

  npm run admin:create -- --database=so7ob --email=you@example.com --name="مدير النظام"

  استبدل البريد. يطبع كلمة عشوائية مرة واحدة؛ لا تحفظها في Git أو المحادثة. الدخول http://localhost:3108/ar/auth/login ثم /ar/admin. الأداة ترفض الإنتاج والاتصال البعيد والوجهة غير المطابقة ووجود مدير أعلى سابق، ولا تعيد إنشاء الحسابات.
- قاعدة MariaDB الاختبارات المستقلة موثقة على loopback:3307، وأسماء so7ob_admin_routes_test وso7ob_admin_e2e_test وso7ob_bootstrap_test. لا تفترض أن العملية ما زالت تعمل؛ افحصها. لا تستخدم قاعدة التطوير أو الإنتاج بدل قاعدة الاختبار.
- المرجع Next المؤقت يعمل فقط من .migration/reference/Website على بيانات اصطناعية منفصلة في .migration/baseline/ وعلى منفذ 3107 عند الحاجة؛ كان متوقفًا عند التسليم. لا تشغّل لقطة المصدر بإعدادات المصدر الإنتاجية.
- .migration/ ملفات عمل محلية ignored، ليست مصدرًا إنتاجيًا وقد لا تتوفر في دردشة أو جهاز جديد؛ أعد إنتاج الاختبارات من الأدوات المتتبعة إذا غابت.

## 8. التحويل والقبول والتسليم

- القرارات المعتمدة: إعادة دخول مرة واحدة عند تحويل منفصل، مع حفظ الحسابات وbcrypt والرموز وأوقات انتهاء/استهلاك أصلية. لا تمدد رمزًا أو تعيد جلسة ملغاة.
- نافذة التراجع الكامل تنتهي قبل إعادة فتح الكتابة. أوقف الكتابات وصفِّ العمليات ثم خذ لقطة نهائية وطابقها واختبر قبل الفتح. بعد الفتح احفظ MariaDB والملفات والطابور والكتابات اللاحقة وتعافَ للأمام؛ لا تستعد SQLite قديمة وتفقد الطلبات. لا Dual Write مرتجل.
- أكمل العمل المستقل إذا منع غياب بيانات الإنتاج أو المراجعة جزءًا آخر، ووثّق المانع. لا تدّع نقل بيانات الخادم أو اكتمال الترحيل الإنتاجي.
- شغّل فعليًا: npm run lint، npm run typecheck، npm test، npm run build، npm run test:e2e، npm run test:infra، git diff --check. أضف/نفذ العقود والتكامل والتزامن والترحيل والعامل والرحلات والقياسات اللازمة. ESLint مستقل عن TypeScript؛ لا تسمِّ فحصًا باسم لا يؤدي وظيفته.
- احتفظ بأدلة موجزة داخل docs/migration/ عن المصدر والخرائط والاستثناءات والمصفوفة والأدوات والمطابقة والاختبارات والقياسات والنشر والنسخ والتحويل والتراجع، وروابط Issues/PRs وحدود التحقق. لا أسرار أو بيانات خاصة في الأدلة.
- ارفع العمل المكتمل إلى web واترك PRs إلى develop جاهزة للمراجعة. تحقق من CI عند SHA الصحيح. ميّز التنفيذ المحلي والرفع ونجاح CI والمراجعة والدمج والإصدار والنشر وترحيل الإنتاج.
- لا تعلن انتهاء المهمة مع وظيفة مفقودة أو اختبار قبول فاشل أو بيانات غير متطابقة أو اعتماد أساسي انتقالي. سلامة Website والتكافؤ مقدمان على مطابقة Rakim الحرفية.

ابدأ الآن بفحص الوضع الحي، واعرض خطة قصيرة مرتبطة بالنواقص ثم تابع التنفيذ. اتخذ القرارات الروتينية ضمن الحدود دون طلب موافقة على كل خطوة، ولا تختزل العمل إلى خطة أو تعِد بناء ما نُفّذ. أي تغيير مدمر أو نشر أو تحويل إنتاجي أو دمج جديد يحتاج تفويضًا مستقلًا.
