# البيانات الدائمة والنسخ والاستعادة

## إعداد التشغيل

الإنتاج يستخدم مثيلًا واحدًا وقرصًا دائمًا. يجب ضبط `DATA_DIR` إلى مجلد مطلق **خارج مجلد الإصدار** و`DATABASE_URL` إلى ملف مطلق داخله وخارج `uploads/` و`backups/`، مثل `/var/lib/so7ob/custom.db`. هذه أمثلة إعداد وليست مسارات إنتاج متحققة. التشغيل عبر `bun run start` يتحقق من المسارات ووجود DB وقابلية القراءة والكتابة قبل تشغيل standalone، ويحافظ على exit status وإشارات الإيقاف. يحتاج artifact أيضًا scripts وsrc/lib/data-paths.ts وBun؛ لا تستخدم server.js مباشرة لتجاوز preflight.

التطوير دون `DATA_DIR` يبقى على `<project>/db/uploads`. URL النسبي `file:../db/custom.db` يُفسَّر نسبة إلى `prisma/schema.prisma` مثل Prisma، وليس نسبة إلى سكربت النسخ. لا تتغير schema أو البيانات بهذه الحزمة. ملفات الأسرار خارج المستودع، ويجب حقن البيئة بواسطة مشرف العملية، بما فيها AUTH_SECRET وSMTP؛ تقييد البريد التجريبي مستقل في Issue #8.

`GET /api/health/ready` يعيد `{ready:true}` فقط عند نجاح اتصال DB وصلاحيات uploads، وإلا 503 دون تفاصيل أو مسارات. هذا لا يثبت مساحة القرص أو صحة كل جدول أو تكامل SMTP، ولا يحل محل smoke test بعد النشر. لا تستطلع المسار بكثافة.

## نقل المسارات عند اعتماد إطلاق الإصدار

1. حدّد مساري DB وuploads الفعليين للإصدار الحالي، خصوصًا standalone. لا تفترض أن الملفات في جذر المشروع ولا تفتح بيانات العملاء لأغراض اختبار.
2. أوقف كل العمليات الكاتبة (خادم وworkers وأدوات الإدارة). تأكد من انتهائها فعليًا؛ المتغير أدناه إقرار تشغيلي وليس قفلًا موزعًا. جهّز نافذة صيانة معتمدة.
3. جهّز نسخة متحققة بالمسار القديم ثم احتفظ بها محميّة خارج الجهاز. لا تنسخ ملف SQLite الحي منفردًا؛ يمكن أن تكون أحدث البيانات داخل WAL.
4. استعد إلى مجلد دائم جديد بالخطوات أدناه، وتحقق من أعداد الجداول وبصمات المرفقات. احتفظ بالمصدر كما هو.
5. اضبط `DATA_DIR` و`DATABASE_URL=file:/.../database.db` للمجلد الجديد، وابدأ مثيلًا واحدًا، ثم تحقق من readiness ورحلة ملفات خاصة ببيانات مصطنعة وتصاريح الأدوار قبل فتح المرور.
6. عند التراجع بعد كتابات جديدة: احتفظ بالمسار الدائم واجعل إصدار التراجع يقرأه، أو انسخ delta مع التحقق تحت توقف الكتابة. إعادة إصدار قديم يعتمد cwd قد تخفي المرفقات الجديدة، ولا تكفي وحدها كتراجع بيانات.

## نسخة كاملة محلية

بعد **إيقاف جميع الكتّاب** وببيئة تشير إلى البيانات المطلوبة:

```bash
BACKUP_WRITES_PAUSED=true bun run db:backup before-migration
```

تنشئ الأداة مجلدًا جديدًا تحت `DATA_DIR/backups` (أو db/backups محليًا): database.db وuploads وmanifest.json. تستخدم `VACUUM INTO` على اتصال read-only للحصول على لقطة SQLite متسقة تشمل WAL، ثم `integrity_check` و`foreign_key_check` وأعداد الجداول والتحقق من وجود كل storedName في Attachment وMediaItem. تُنسخ جميع الملفات بما فيها غير المرتبطة تجنبًا لفقدها؛ الملفات الرمزية/المجلدات غير متوقعة ومرفوضة. يُنشر مجلد النسخة بعد اكتمال التحقق؛ الفشل يحذف المجلد الجزئي ويخرج برمز غير صفري.

المجلدات الجديدة 0700 والملفات 0600. manifest يحوي أسماء تخزين وأعدادًا وبصمات، لذلك يُعامل هو والنسخة كبيانات خاصة. لا توجد بيانات محتوى أو رموز في إخراج النجاح. البصمات تكشف التلف العرضي، وليست توقيعًا ضد مهاجم يغيّر النسخة والmanifest معًا. لا تخزن backups داخل Git؛ ignores وقائية ولا تحمي مسار DATA_DIR عشوائيًا داخل مستودع آخر.

هذه **نسخة محلية غير مشفرة** لا تحمي من فقد الجهاز. قبل الاعتماد التشغيلي يلزم تحديد مسؤول النسخ وRPO/RTO والاحتفاظ وإعداد نسخة مشفرة خارج الجهاز والتحقق من تنزيلها وفكها واستعادتها. لم يُختَر مزود ولم تُنشأ جدولة أو خدمة خارجية. احتفظ بعدة أجيال متحققة، ولا تحذف المصدر أو الأجيال القديمة تلقائيًا.

## تمرين الاستعادة

```bash
bun run db:restore /absolute/snapshot /absolute/new-empty-data-directory
```

يجب ألا يوجد مجلد الهدف أصلًا. تتحقق الأداة من manifest وSHA256 وأعداد الجداول وSQLite والمرفقات، وتعيد التحقق بعد النسخ ثم تنشر المجلد الجديد. لا تبدأ الخادم أو تستبدل DB موجودة. اضبط DATABASE_URL لاسم `database.db` الناتج. نفّذ التمرين أولًا في بيئة محلية معزولة وببيانات مصطنعة؛ عطّل SMTP وwebhook ولا تتصل بتكاملات حقيقية. قِس زمن النقل والتحقق وتشغيل التطبيق لتحديد RTO واقعي؛ لا تُعتبر مدة اختبار صغير قدرة إنتاج مثبتة.

## التحقق الآلي وحدوده

`bun run test` يشمل Vitest واختبارات Bun لأداة SQLite؛ `bun run typecheck` يشمل السكربتات الجديدة. CI يثبت Node24.21.0 وBun1.4.2 لتوافق jsdom/Vitest الحاليين دون تغيير الحزم أو lock. تغطي الاختبارات WAL غير checkpointed، استعادة الصفوف والملفات، تلف/فقد المرفقات، رفض الكتابة إلى نظام ملفات read-only، وعدم استبدال الهدف. اختبار read-only لا يُوصف بأنه قياس ENOSPC أو انقطاع طاقة؛ يجب إجراء تمرين امتلاء قرص على volume مخصص قبل الإنتاج. ضمان DB+files يعتمد إيقاف الكتابة الموثق، ولا يوفر zero-downtime snapshot.

المراجع: [SQLite VACUUM INTO](https://sqlite.org/lang_vacuum.html)، [Bun SQLite](https://bun.sh/docs/runtime/sqlite)، [SQLite WAL](https://sqlite.org/wal.html). تحقق 2026-10-02.
